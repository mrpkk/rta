# PROGRESS — ṚTA

> Правило: каждый шаг — **вертикальный слайс** (реализация + тест + зелёный прогон + коммит + push).
> Старт сессии: читать этот файл → взять первый незакрытый `- [ ]` → выполнить → обновить чекбокс → commit + push.
> Команда верификации: `python3 -m pytest -q` (49 passed) и `node build/verify-service.mjs` для проверки доказательств.
> Закрытый слайс = зелёный тест + коммит с хешем. Иначе не закрыт.

**Текущее состояние (09.10.2026):** 49 тестов зелёные. Пять схем Groth16 компилируются и проверяются, у каждой свой ключ. HTTP-сервис отвечает, платёжный путь прогнан **вживую на Base Sepolia**: челлендж → подпись EIP-712 → разбор фасилитатором → проверка подписи → ончейн-проверка баланса. Останавливается на `invalid_exact_evm_insufficient_balance` — то есть не хватает только USDC на тестовом кошельке. Всё остальное в цепочке работает.

Файл создан 09.10.2026 — до этого прогресса не существовало, хотя правило требовало его с самого начала. Это и было причиной, почему состояние продукта приходилось восстанавливать по коду и логам.

      генератора не доходила. Коммит исправлений — `b792dce`. `ceremony-log.json` содержит старые строки-сиды

## КРИТИЧНО: v2-платежи отвергались фасилитатором (найдено и исправлено 17.10.2026)

`/settle`-запрос слал в `paymentRequirements` поле `maxAmountRequired` — это поле
схемы **v1**. Клиент объявляет `x402Version: 2`, фасилитатор PayAI классифицирует
требования как v1 и отказывает:

> `invalid_payment_requirements`: «x402Version 2 requires V2 payment requirements
> ('amount'); got V1 ('maxAmountRequired')»

**Живой платёж по этой форме был бы отвергнут — до списания и до услуги.**
Проверено вживую 17.10.2026 против `facilitator.payai.network/settle`: с полем —
отказ; без поля — доходит до проверки подписи. Прежний комментарий («без amount
фасилитатор отвечает 500») был верен только про отсутствие `amount`; присутствие
`maxAmountRequired` теперь ломает v2-валидацию.

**Исправлено:** из `paymentRequirements` убрано `maxAmountRequired`.
Тесты: **72 passed**. Тот же дефект найден и исправлен в `attest` (`7f73642`)
и `drift` (`0f0690c`).

## Риск выручки: платёж до проверки (16.10.2026)

Порядок в `do_POST` проверен по коду:

1. нет заголовка оплаты → `402` со счётом
2. **устаревший nonce → `409`, `paid: false`** — до обращения к фасилитатору,
   чтобы заведомо отвергаемый запрос не тратил сеть
3. `settle_payment(...)` → **расчёт состоялся**
4. `verify_paid(...)` → проверка доказательства; квитанция с `transaction`
   уходит клиенту в любом случае

Клиент платит 1 USDC **до** того, как мы проверим доказательство, и возврата
нет. `verify_paid` честно прикладывает квитанцию даже при отказе: платёж был.

Опасный сценарий не «клиент прислал плохое доказательство» — это его выбор.
Опасный — **наша ошибка проверки при валидном доказательстве**: клиент
заплатит за `ok: false`, причина которого наша. Так уже случалось — в коде
записано, что четыре схемы из пяти сверялись с чужим ключом и отвергали
валидные доказательства.

**Что с этим делать:** возврат по квитанции вручную. Пока не сделано.
